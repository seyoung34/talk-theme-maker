# scripts/capture

웹 편집기 화면을 영상으로 찍는 러너. 가이드 영상과 홍보 릴스가 같은 골격을 쓴다.

```powershell
# 기본: Supabase를 비운 채로 빌드하고 기동해서 찍는다 (몇 분 걸린다)
node scripts/capture/run.mjs --profile=guide

# 이미 서버가 떠 있으면 그걸 쓴다 (반복 실행할 때)
node scripts/capture/run.mjs --profile=guide --server=http://127.0.0.1:3311 --scenes=editor-tour
```

| 인자 | 뜻 |
|---|---|
| `--profile=guide\|guide-mobile\|reel` | 촬영 규격. 기본 `guide` |
| `--scenes=a,b` | 찍을 씬. 기본은 mock 환경에서도 도는 구성 |
| `--env=mock\|local` | 촬영 백엔드. 기본 `mock` |
| `--server=<url>` | 이미 떠 있는 서버 사용. 빌드·기동을 건너뛴다 |
| `--out=<dir>` | 출력 경로. 기본 `E:\TalkTheme-자료\촬영본\<profile>` |
| `--backend=screencast\|screenshot` | 프로필 기본 백엔드를 덮는다 |
| `--tone-down=0.08` | 배경 토큰만 그만큼 어둡게 (릴스용) |
| `--safe-guides` | 인스타·틱톡 안전영역 가늠자를 그린다 (확인용) |
| `--keep-frames` | 중간 프레임을 지우지 않는다 (다시 인코딩할 때) |
| `--no-build` | 빌드를 건너뛴다. **아래 주의 참고** |

## 촬영 환경 두 가지

```powershell
npm run capture -- --profile=guide                # mock (기본)
npm run capture -- --profile=guide --env=local    # 로컬 Supabase
```

| | `mock` | `local` |
|---|---|---|
| Supabase | 비움 | 로컬 스택 |
| 시스템 템플릿·추천 에셋 | **안 보임** | 보임 |
| 결정론 | 완전 | fixture에 의존 |
| 쓰는 씬 | 편집기만 보여 주는 씬 | 갤러리·추천 에셋·말풍선 |

`local`은 `npm run dev:local`과 **같은 `.env.supabase-local`을 읽습니다.** 두 곳이 다른 값을 쓰면
"개발에서는 보이는데 촬영에는 안 나오는" 차이가 생깁니다.

`local`로 찍기 전 준비:

```powershell
npx supabase start
node scripts/seed-local-users.mjs
node scripts/capture-fixtures.mjs seed
```

스택이 꺼져 있으면 **촬영을 시작하기 전에** 위 명령을 안내하며 멈춥니다. 갤러리가 빈 채로 찍히는
실패는 촬영이 끝난 뒤에야 드러나기 때문입니다.

## 왜 Supabase를 비우고 찍나

`playwright.config.ts`가 E2E에서 하는 것과 같다. 크레딧이 소모되지 않고, 같은 명령이 같은 화면을
낸다. 운영 Supabase에 붙여 찍지 않는다.

`NEXT_PUBLIC_*`은 **빌드 시점에 번들로 구워진다.** 기동할 때만 비워서는 소용이 없다.
`--no-build`가 위험한 이유가 이것이다 — 이전 빌드에 개발자의 운영 키가 들어 있을 수 있다.

## 해상도 상한 (실측)

뷰포트 1280×720 / `deviceScaleFactor` 1.5에서 네 모서리 색으로 판정한 결과다.

| 경로 | 결과 |
|---|---|
| `page.screenshot()` | 1920×1080, 정상 |
| `recordVideo({ size })` | 1920×1080 컨테이너, 좌상단만 그리고 나머지 `#808080` |
| `page.screencast({ size })` | 위와 같음 |
| `page.screencast`, `size` == 뷰포트 | 꽉 참 |

**screencast의 실해상도는 뷰포트 CSS 픽셀이다.** `size`는 컨테이너만 키우고 `deviceScaleFactor`는
무시한다. `size`를 생략하면 Playwright가 800px 상자로 줄이므로(1280×720 → 800×450) 뷰포트와 같은
값으로 반드시 준다.

## 촬영 뷰포트 (규격과 다른 값이다)

출력은 1920×1080이지만 **뷰포트는 1536×864**다. 둘을 헷갈리면 안 된다 — 출력은 파일 크기고,
뷰포트는 편집기가 어떤 레이아웃으로 그려지느냐다.

| | 뷰포트 | dsf | 출력 |
|---|---|---|---|
| 가이드 | 1536×864 | 1.25 | 1920×1080 |
| 가이드 모바일 · 릴스 | 432×768 | 2.5 | 1080×1920 |

편집기는 **1024 / 1280 / 1536**에서 단이 갈린다(`ProjectImporterClient`의 `lg` `xl` `2xl`).
1536부터가 오른쪽 패널 320px짜리 마지막 단이고, FHD 모니터를 전체화면으로 쓰는 사람이 보는 것이
이 단이다. 1280으로 찍으면 패널 폭부터 다른 화면을 따라 하라고 시키게 된다.

단이 바뀌어도 **나타나거나 사라지는 요소는 없다.** `lg:hidden` `xl:block`은 두 폭에서 같게
동작하고 `2xl`은 그리드 폭만 바꾼다. 그래서 씬 선택자는 손대지 않았다.

뷰포트를 키우면 같은 출력 안에서 글자가 작아진다(dsf가 그만큼 내려간다). 그래서 **가이드 카드
폭이 먼저 확보되어야 올릴 수 있는 값이다** — 카드가 2단이던 시절에는 자료가 698px로 줄어
편집기 11px 라벨이 5px가 됐다. 카드를 세로로 쌓아 1148px을 확보한 뒤라 지금은 8px대다.

출력 픽셀 수가 그대로라 **한 장당 촬영 비용은 변하지 않는다.**

## 백엔드 두 가지

| | `screencast` | `screenshot` (양쪽 프로필 기본) |
|---|---|---|
| 해상도 | 뷰포트 CSS 픽셀이 상한 | `deviceScaleFactor`만큼 올라간다 |
| 실측 | 1280×720 @25fps | 가이드 1920×1080 · 릴스 1080×1920 @30fps |
| 커서·클릭 강조 | `showActions` 내장 | `ctx.click`이 DOM으로 그린다 |
| 프레임 단위 구동 | 못 한다(시간으로 흉내) | 한다 |
| 로딩 구간 버리기 | 못 한다 → manifest `skip`으로 표시 | 프레임을 아예 안 만든다 |

한동안 **해상도와 커서 중 하나를 골라야 하는** 것처럼 보였다. `showActions`는 screencast 전용인데
screencast는 1280×720이 상한이기 때문이다. 커서를 자막과 같은 방식으로 DOM에 직접 그리면서
그 맞바꿈이 없어졌다 — 지금은 양쪽 프로필 모두 `screenshot`을 쓴다.

`meetsSpec`이 규격 도달 여부를 manifest에 남긴다. `--backend=screencast`로 되돌릴 수 있다.

## 커서 (가이드의 핵심)

**가이드 영상에 커서는 선택이 아니다.** 어디를 누르는지 보이지 않으면 보는 사람이 자기 화면에서
같은 곳을 찾을 수 없다. `ctx.click(locator)`이 커서를 목표까지 움직이고, 누르는 순간 파문을 찍고,
결과가 나타날 시간을 준 뒤 넘어간다.

- 커서는 흰 채움 + 검은 테두리 + 그림자다. 이 앱은 밝은 편집 화면과 어두운 미리보기가 한 프레임에
  같이 나오므로 한쪽 색만으로는 반드시 어딘가에서 묻힌다.
- 파문은 CSS 애니메이션이라 배속 촬영에서 CDP가 함께 늦추고 인코딩이 되돌린다.
- **모바일 프로필에서는 화살표를 그리지 않는다.** 손가락으로 누르는 화면에 마우스 커서가 있으면
  안 된다. 파문만 남는다.
- `showActions`가 있는 백엔드에서는 그리지 않는다 — 커서가 두 개로 보인다.

## 가이드는 데스크톱·모바일 두 벌

폰으로 가이드를 보는 사람은 대개 **폰으로 편집도 합니다.** 데스크톱 편집기 화면을 390px 폭 카드에
넣으면 글자를 읽을 수 없고, 읽었더라도 자기 화면에 없는 UI라 따라 할 수가 없습니다.

```powershell
npm run capture -- --profile=guide          # 1920x1080, 화살표 커서
npm run capture -- --profile=guide-mobile   # 1080x1920, 파문만 (폰에 마우스는 없다)
```

씬 id가 두 프로필에서 같습니다(`choose-screen`, `change-color`). 파일명은 프로필이 갈라 주고,
`content.ts`에서 같은 스텝의 `media`(데스크톱)와 `mobileMedia`(모바일)로 짝이 됩니다.

가이드 페이지는 **편집기와 같은 기준(1024px)** 으로 자료를 고릅니다. 기준이 어긋나면 화면에 없는
UI를 따라 하라고 시키게 됩니다.

**비율은 자료가 들고 다닙니다.** 카드가 `object-cover`라 비율이 어긋나면 오류 없이 잘리기만 하므로,
`content.ts`의 `media.aspect`를 프로필의 `aspect`와 같은 값으로 적습니다(`16 / 9` · `9 / 16`).

## 씬마다 파일 따로 (`splitScenes`)

가이드는 씬 하나가 `/guide` 스텝 하나이고 **파일도 따로 나간다**. `EasyStep.media.src`가 파일
하나를 가리키기 때문이다. 한 편으로 이어 붙이면 스텝에 꽂을 수가 없다.

```
guide-choose-screen.mp4   guide-choose-screen-poster.webp
guide-change-color.mp4    guide-change-color-poster.webp
```

덕분에 **편집 UI가 바뀌어도 바뀐 스텝만 다시 찍으면 된다.**
릴스는 반대로 한 편으로 이어 붙이고(`splitScenes: false`) 씬 경계만 manifest에 남긴다.

## 배속 촬영 (screenshot 백엔드)

1080×1920 JPEG 한 장에 약 52ms라 19fps가 상한이다. 30fps를 채우려고 페이지를 `slowdown`배 느리게
연출하고 인코딩에서 시간축을 같은 비율로 되돌린다(19 × 1.6 = 30.4fps).

- CSS 트랜지션·`@keyframes`는 CDP `Animation.setPlaybackRate`가 함께 늦춘다. 애니메이션을 **끄지
  않는다** — 색이 바뀌는 순간 같은 움직임은 잘라낼 대상이 아니라 보여주려는 내용이다.
- `ctx.beat(ms)`는 배속만큼 실제로 더 기다린다. 그래야 최종 영상에서 의도한 길이가 된다.
- 프레임 간격이 일정하지 않아서 concat 디먹서에 **프레임마다 실제 표시 시간**을 적어 넘긴다.
  고정 레이트로 이어 붙이면 움직임이 미세하게 밀린다.

## 씬이 쓰는 도구

**단위는 전부 최종 영상 기준 초다.**

| | 설명 |
|---|---|
| `click(locator)` | 커서를 옮기고, 파문을 찍고, 누르고, 결과를 보여준다 |
| `point(locator)` | 누르지 않고 가리키기만 |
| `hold(seconds)` | 움직임 없이 머문다 |
| `scrollTo(y\|"bottom"\|"top", { seconds })` | 스크롤을 굴린다 |
| `caption(text)` | 자막. 하단 안전영역 위에 앉는다. `null`이면 지운다 |
| `offCamera(fn)` | 이동·부트스트랩처럼 **보여줄 것 없는 구간**을 감싼다 |
| `dismissNotices()` | 편집기 진입 토스트를 닫는다 |
| `frameStep(count, fn)` | 프레임마다 `fn`을 한 번 부른다 (직접 연출용) |

**머무는 시간은 초로, 움직임은 프레임으로.** 둘의 기준이 다른 데는 이유가 있다.

최종 길이는 프레임 **개수**가 아니라 **촬영 시각**으로 정해진다. 그래서 `hold`를 프레임 수로 세면
촬영이 느린 환경에서 영상이 그만큼 길어진다 — 실제로 6초로 의도한 스텝이 dev 서버에서 13초로
나왔다. 시간으로 기다리면 촬영 속도와 무관하게 의도한 길이가 나온다.

반대로 커서 이동·스크롤 같은 **움직임**은 프레임으로 나눠야 한다. 부드러움은 프레임 개수가
정하고, 스크린샷 루프가 렌더러를 점유해 `requestAnimationFrame`이 굶기 때문이다(§2.6 5번) —
9.6초로 의도한 스크롤이 27초 걸린 적이 있다.

> 길이를 정확히 맞추려면 **프로덕션 빌드로 찍는다.** dev 서버는 렌더가 느려 캡처율이 크게
> 떨어진다(측정 6fps 대 설계 19fps). 선택자를 다듬는 동안에만 dev를 쓰고, 배포본은 빌드해서 찍는다.

`offCamera`를 안 쓰면 릴스 앞머리가 로딩 화면으로 몇 초 날아간다. 실제로 첫 촬영본의 3초 지점이
아직 편집기를 그리는 중이었다(16.2초 → 12.8초로 줄었다).

## 안전영역과 자막

인스타·틱톡 UI가 상단 약 14%, 하단 약 22%를 덮는다. 자막은 하단 안전영역 **위**에 앉힌다
(실측 70.3%~76.0%, 경계는 78%). `--safe-guides`로 가늠자를 그려 확인할 수 있다.

자막을 ffmpeg `drawtext`가 아니라 DOM으로 그리는 이유는 둘이다. 윈도우 한글 폰트 문제를 피하고,
앱의 폰트를 그대로 써서 브랜드가 저절로 맞는다.

## 배경 톤다운 (릴스 전용)

화면의 90% 이상이 최고 휘도 구간에 몰려 있고 파랑이 빨강보다 4.5레벨 높다. 인스타·틱톡 압축은
밝고 평평한 면에서 밴딩이 잘 생기므로 톤다운은 화질에도 이득이다.

**`filter: brightness()`를 화면 전체에 걸지 않는다.** 버튼과 브랜드 노랑까지 죽는다. 배경·surface
토큰만 값으로 바꾼다 — `--tone-down=0.08`에서 `--color-background`는 `#e8f1ff` → `#d5deeb`,
브랜드 `#fee500`은 그대로다.

**가이드에는 쓰지 않는다.** 제품 화면과 다르면 사용자가 자기 화면에서 같은 곳을 못 찾는다.

## 촬영 함정

러너가 자동으로 처리한다. 씬마다 다시 구현하지 않는다.

| 함정 | 대응 |
|---|---|
| 분석 동의 배너가 하단을 덮는다 | 동의값을 미리 `denied`로 심고 CSS로도 지운다 |
| 거부하면 쿠키 설정 버튼이 좌하단에 **상주**한다 | 같은 CSS가 함께 지운다 |
| Next dev 표시등(`nextjs-portal`) | CSS로 지운다 |
| 스크롤바가 회색 띠로 찍힌다 | 폭 0. 스크롤은 그대로 동작한다 |
| 편집기 진입 토스트 | `ctx.dismissNotices()`로 닫는다 |
| 주입한 커서가 렌더되지 않는다 | `screencast.showActions()`를 쓴다 — 브라우저 바깥에서 그린다 |
| `article[role="button"]`이 0개를 잡아 클릭이 조용히 건너뛰어진다 | 갤러리 씬이 카드 0개면 **던진다** |
| 카드 클릭은 상세 모달만 연다 | 갤러리 씬이 "Android로 시작"을 한 번 더 누른다 |

**씬이 끝날 때마다 `assertCleanChrome`이 위 장식이 실제로 안 보이는지 확인하고 던진다.**
이 함정들의 공통점은 조용히 실패한다는 것이다 — 배너가 찍혀도 촬영은 끝까지 돌고, 다 만든 뒤에야
프레임에서 발견된다.

## 구조

| 파일 | 역할 |
|---|---|
| `run.mjs` | CLI. 인자 파싱, 서버 빌드·기동 |
| `runner.mjs` | 브라우저 기동, 함정 대응, 씬 실행, 경계 시각, manifest |
| `profiles.mjs` | 규격(뷰포트·백엔드·출력). 해상도 값은 전부 실측 근거를 주석에 둔다 |
| `backends/` | 캡처 방식. 규격마다 해상도 상한이 달라 한 방식으로 둘 다 찍을 수 없다 |
| `pageSetup.mjs` | 페이지에 주입하는 함수. 브라우저 안에서 단독 성립해야 한다 |
| `overlays.mjs` | 자막·챕터·안전영역 가늠자, 배경 톤다운 |
| `encode.mjs` | ffmpeg 탐색·실측·mp4/webp 변환, 프레임 묶음 인코딩 |
| `scenes/` | 씬 모듈과 레지스트리 |

`scenes/shared.mjs`는 `e2e/fixtures/*.ts`와 **같은 화면을 가리키는 코드가 두 벌**이다. 스크립트가
`.mjs`라 TypeScript fixture를 그대로 가져올 수 없어서다. 편집기 마크업을 바꾸면 두 곳을 함께 고친다.

## ffmpeg

정식 빌드가 필요하다. Playwright 번들 빌드는 축소판이라 mp4·webp·색보정을 만들지 못한다.

```powershell
winget install Gyan.FFmpeg
```

설치한 그 셸에서는 PATH에 잡히지 않는다. **새 터미널을 열어야** 보인다.
`encode.mjs`는 PATH에 없으면 winget 설치 경로를 직접 찾고, 그래도 없으면 위 안내와 함께 던진다.

## manifest

캡처가 끝나면 `capture-manifest.json`을 남긴다. 합성(Remotion) 쪽은 이 파일만 읽는다.

`measured`는 프로필이 **의도한** 값이 아니라 `clips[].path`가 가리키는 그 파일을 실제로 잰 값이다.
백엔드가 뷰포트에 묶여 있어 의도와 결과가 갈리는데, 거기에 의도한 값을 적으면 manifest가 거짓말을
하게 된다.

`clips[].startSec`/`endSec`는 **최종 영상 기준**이다. 배속으로 찍었으면 그만큼 앞당겨 적는다.

`clips[].skip`은 볼 것이 없는 구간이다. 프레임을 실제로 버리는 백엔드에서는 항상 비어 있고,
실시간 녹화에서는 로딩 구간이 여기 들어온다. 합성 쪽은 이 구간을 잘라내고 이어 붙인다.
