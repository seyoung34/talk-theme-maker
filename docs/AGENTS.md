# docs

프로젝트 문서 저장소. 코드가 아니라 "왜 이렇게 만들었는지 · 지금 뭘 하고 있는지"를 다룬다.
사람보다 AI 에이전트가 먼저 읽는다고 가정하고 분류·갱신 규칙을 지킨다.

문서를 찾을 때는 먼저 [README.md](README.md) 인덱스를 본다. 이 파일은 "새 문서를 어디에 두고,
언제 상태를 바꾸고, 언제 커밋하는지"에 대한 규칙만 다룬다.

## 디렉토리 구조

```
docs/
├── architecture/   # 설계·데이터 모델·UX 흐름 — 상태(진행 여부)와 무관하게 항상 참조되는 문서
├── setup/          # 환경 구성·운영 안내 (Supabase 등)
├── report/         # 코드 리뷰·진단 스냅샷 — 특정 시점 기록, 상태 전환 없음 (후속 계획은 plans로 분리)
├── notes/          # 형식 없는 메모·아이디어·가벼운 TODO — 아래 "notes" 절 참조
└── plans/
    ├── planned/       # 기획/방향 확정, 구현 착수 전
    ├── in-progress/   # 구현 진행중 (phase/마일스톤 체크리스트 보유)
    └── done/          # 구현 및 검증 완료, 히스토리로 보존
```

## 분류 규칙 (planned / in-progress / done)

- **planned**: 방향은 확정됐지만 코드 변경이 아직 시작되지 않은 문서. 문서 상단에
  `> 상태: 기획 확정. 구현 착수 전.` 형태로 명시한다.
- **in-progress**: 코드 변경이 시작된 문서. Phase/마일스톤 체크리스트(`- [ ]`/`- [x]`)를 갖는 것이 기본형이다.
  체크리스트가 없는 계획 문서라도 구현이 진행중이면 여기에 둔다.
- **done**: 계획된 범위의 구현과 검증(로컬/배포 실기기 등 문서가 요구한 검증)이 끝난 문서.
  "구현은 끝났지만 후속 과제가 남음"은 done 유지 + 상태 라인에 후속 과제를 별도로 적는다(new plan 문서로 분리해도 됨).
  범위 자체가 재정의되어 별도 문서로 대체된 경우도 done으로 옮기고 상태 라인에 대체 문서를 링크한다.

판단이 애매하면(예: 절반만 완료) **문서가 정의한 "완료 기준"을 기준으로** 판단한다. 완료 기준이 없는 문서는
새로 작성할 때 반드시 완료 기준을 명시한다.

## 문서 상태 라인 규격

모든 `plans/*` 문서는 제목 바로 아래에 blockquote 상태 라인을 둔다.

```markdown
> 상태: <현재 상태 한 줄 요약>. <남은 것/다음 단계>.
> 참고: <관련 문서> → [상대경로](상대경로)
```

- 다른 계획 문서를 링크할 때는 반드시 **상대경로**를 쓴다. 문서를 옮길 때(`git mv`) 그 문서를 가리키는
  다른 모든 문서의 링크도 같은 커밋에서 함께 고친다 (`grep -rn "문서파일명.md" docs/` 로 역참조 확인).
- `docs/` 바깥에서 경로를 참조하는 파일(예: `.omo/plans/*.md`의 executor 참조 목록)도 같은 커밋에서 갱신한다.

## in-progress 문서의 phase 관리 규칙

`plans/in-progress/` 문서는 phase/마일스톤별 체크리스트를 최신 상태로 유지한다.

1. **phase 하나가 실제로 끝나면, 그 자리에서 바로** 해당 체크박스를 `- [x]`로 갱신한다. 코드 커밋과
   문서 체크박스 갱신을 분리해서 나중에 몰아 하지 않는다 — 몰아서 하면 "코드는 있는데 문서는 옛날 상태"인
   채로 다음 에이전트가 잘못된 전제로 작업을 시작한다.
2. 체크박스를 갱신할 때 **완료 기준 문구도 같이 검토**한다. 완료 기준이 그 phase의 실제 산출물과
   달라졌으면 문구를 고친다(체크박스만 채우고 기준 문구를 방치하지 않는다).
3. 문서 상단 상태 라인은 "지금 어느 phase까지 끝났고 무엇이 남았는지"를 항상 한 줄로 반영한다. 개별
   체크박스만 갱신하고 상단 요약을 방치하지 않는다.
4. **문서의 모든 phase가 끝나고 완료 기준을 충족하면, 같은 커밋에서**:
   - 상태 라인을 완료로 갱신
   - `git mv`로 `plans/done/`으로 이동
   - 그 문서를 참조하던 다른 문서·README 인덱스의 링크/분류를 갱신
   진행 상황 갱신과 done 이동을 별도 커밋으로 나누지 않는다. 이동이 누락되면 완료된 작업이
   in-progress로 계속 보여 다음 에이전트가 다시 손대게 된다.
5. **커밋 메시지**: phase 완료를 반영하는 커밋은 코드 커밋과 분리해도 되지만, 분리한다면
   `docs(plans): mark <문서/phase> complete` 형태로 무엇이 끝났는지 명확히 쓴다. 코드 커밋에 문서 갱신을
   함께 담아도 무방하다(오히려 권장 — phase 완료와 문서 상태가 어긋날 시간을 없앤다).

## planned → in-progress 전환

구현에 실제로 착수하면(첫 커밋이 나가면) 그 시점에 상태 라인을 갱신하고 `git mv`로
`plans/in-progress/`로 옮긴다. "착수 예정"과 "착수함"을 문서 위치로 구분한다.

## notes — 형식 없는 메모

`docs/notes/`는 위 분류·상태 라인 규칙의 적용 대상이 **아니다**. 사용자가 그때그때 적는 아이디어,
가벼운 TODO, 나중에 다시 볼 메모를 아무 형식 없이 쌓아두는 곳이다.

- 제목·상태 라인·완료 기준 같은 규격을 요구하지 않는다. 파일 하나에 여러 항목을 자유롭게 추가/삭제해도 되고,
  새 파일을 몇 개를 만들어도 상관없다.
- 여기 있는 메모를 읽고 **정식 계획 문서로 격상**할 가치가 있다고 판단되면(범위가 커지거나 여러 phase가
  필요해지면) `docs/plans/planned/`에 새 문서를 만들고, 격상된 원본 메모 항목은 지운다. 메모 파일 자체를
  `git mv`로 옮기지 않는다 — 메모는 형식이 없고 계획 문서는 상태 라인·완료 기준을 갖춰야 하므로 새로 쓴다.
- **가벼운 버그 수정이나 작은 기능 추가는 문서화 없이 바로 코드로 구현한다.** `docs/notes/`에 적힌 메모라도
  구현 범위가 한 커밋짜리로 작고 명확하면, 계획 문서를 만들지 말고 바로 고치고 메모 항목을 지운다.
  문서화가 필요한 경우는 여러 phase로 나눠야 하거나, 설계 결정이 필요하거나, 다른 에이전트가 맥락 없이
  이어받을 가능성이 있을 때뿐이다.
- 메모를 실제로 구현했으면(정식 문서로 만들었든, 바로 코드로 처리했든) 처리된 항목은 지운다. 메모는
  "지금 아직 안 한 것"만 담아야 쓸모가 있다.

## README.md(인덱스) 갱신 규칙

문서를 추가·이동·상태 전환할 때는 **같은 커밋에서** `docs/README.md`의 해당 항목도 갱신한다.
인덱스가 실제 파일 위치/상태와 어긋나면 인덱스의 존재 의미가 없다.
