## 배경과 현재 결정

2026-07-13 출시 준비도 진단에서 다섯 가지 P0 위험을 확인했다. 그중 시스템 템플릿 지식재산권 문제는
다음과 같이 우선 조치했다.

- 문제 소지가 있는 시스템 템플릿은 일반 갤러리에서 노출되지 않도록 비공개 처리했다.
- 앞으로 공개하는 시스템 템플릿은 운영자가 저작권·상업적 이용 범위를 확인한 콘텐츠로 추가한다.
- 저작권에 문제가 없는 신규 템플릿 제작과 라인업 구성은 운영자 작업으로 진행한다.

이 문서는 위 조치를 전제로 진단 보고서의 **나머지 문제**를 해결한다. 공개 유료 출시를 막는 P0 작업과
출시 후 전환을 높이는 P1 작업을 분리하며, P0 완료 전에는 불특정 다수를 대상으로 유료 트래픽을 확대하지
않는다.

## 목표와 범위

### 목표

- 사용자가 보는 개인정보·계정 저장·결제 안내를 실제 시스템 동작과 일치시킨다.
- 결제 취소·환불·영수증·탈퇴 요청을 운영자가 일관되게 처리할 수 있게 한다.
- 인증·결제·내보내기 장애와 데이터 손실을 출시 전에 발견하고 대응할 수 있게 한다.
- 지원 대상 Android/iOS 조합과 고객지원 범위를 검증 결과로 명시한다.
- P0 완료 후 가격 안내, 초보 편집 흐름, 모바일, SEO를 단계적으로 개선한다.

### 이번 계획에서 제외하는 것

- 시스템 템플릿 이미지 자체의 제작과 저작권 판단
- 사용자 공개 갤러리와 사용자 간 템플릿 공유
- 모든 프로젝트의 자동 클라우드 동기화
- GA4 이벤트·대시보드 자체 구현: `service-growth-plan`에서 계속 관리한다.
- 로그인·충전 이탈 자동 복구 자체 구현: `editor-draft-recovery-plan`에서 계속 관리한다.

## 출시 원칙과 의사결정

1. **정책은 실제 동작 뒤에 맞추지 않는다.** 데이터 처리·보관·삭제 동작을 먼저 확인하고 정책 문구를
   그 동작과 일치시킨다.
2. **로컬 우선을 기본값으로 유지한다.** 계정에는 크레딧·결제·내보내기 이력을 보관하고, 편집 프로젝트는
   사용자가 명시적으로 백업하기 전까지 현재 브라우저에 보관한다.
3. **환불은 결제 상태 덮어쓰기가 아니라 별도 원장으로 기록한다.** 지급·사용·회수 이력이 감사 가능해야 한다.
4. **지원 범위 밖 조합을 암묵적으로 보증하지 않는다.** 검증된 OS·카카오톡 조합과 알려진 제한을 공개한다.
5. **P0는 출시 게이트, P1은 성장 작업이다.** P0 완료 판정과 제한적 유료 출시 후에 P1 실험을 확대한다.

## Phase 1 — 데이터 처리 투명성·정책·동의

### 구현

- [x] 편집, 사용자 템플릿 저장, iOS export, Android 비동기 export, 결제, 인증, 분석의 데이터 흐름표를
  작성한다. 각 단계에 처리 주체, 전송 데이터, 저장 위치, 보관 기간, 삭제 방법을 기록한다.
- [x] 편집·저장 화면의 “서버에 업로드되지 않는다” 문구를 “편집과 내 템플릿 저장은 현재 브라우저에서
  처리하며, 내보내기 시 파일 생성을 위해 서버로 일시 전송한다”는 의미로 통일한다.
- [ ] Android 입력·출력 GCS 객체의 lifecycle 설정과 실제 삭제 여부를 샘플 객체로 검증하고 결과를
  운영 문서에 남긴다.
  - 2026-07-14 운영 설정 확인 완료: 입력 1일, 출력 7일 Delete 규칙. 기한 경과 후 샘플 객체 부재 실측 대기.
- [x] PayApp `raw_payload` 저장 필드를 allowlist로 축소하고 개인정보 가능 필드를 마스킹한다. 원문 보관이
  필요한 필드는 목적과 보존 기간을 별도로 명시한다.
- [x] `/terms`, `/privacy`, `/refund`, `/support`, 저작권 신고 안내 페이지를 만들고 전역 footer와 결제 전
  화면에서 접근할 수 있게 한다.
- [x] 회원가입을 이용약관·개인정보 처리방침의 명시적 동의 구조로 바꾸고 정책 버전·동의 시각을 저장한다.
- [x] 이메일 회원가입과 신규 계정 생성 가능성이 있는 카카오 인증에서 만 14세 이상 확인을 필수화하고 확인 이력을 저장한다.
- [ ] 사업자 정보, 고객지원 연락처, 운영 시간, 문의·권리침해·개인정보 요청 접수 경로를 노출한다.
  - 토비토비 사업자·대표자·등록번호·주소와 현재 문의처 입력은 완료. 통신판매업 신고번호·운영 시간 입력과 실제 수신 확인이 남음.

### 완료 기준

- 화면 안내, 개인정보 처리방침, 실제 네트워크·저장 동작의 내용이 서로 모순되지 않는다.

- 결제와 회원가입 전에 약관·개인정보·환불·사업자·지원 정보를 확인할 수 있다.
- 정책 문서는 실제 사업자 정보와 운영 방식을 반영한 뒤 법률 전문가의 최종 검토를 받는다.

## Phase 2 — 계정 약속 정렬·프로젝트 백업·탈퇴

### 구현

- [ ] 로그인·마이페이지 문구를 “크레딧과 내보내기 이력은 계정, 내 템플릿은 현재 브라우저”라는 실제
  저장 범위에 맞게 수정한다.
- [ ] 내 템플릿 저장 시 브라우저 데이터 삭제·기기 변경·시크릿 모드에서 작업이 사라질 수 있음을
  과도하게 방해하지 않는 안내로 표시한다.
- [ ] 이미지, 색상, 후보 선택, 말풍선 보정, 플랫폼·템플릿 식별자를 포함하는 프로젝트 백업 파일

- [ ] 백업 파일에 스키마 버전과 무결성 검증을 추가하고, 알 수 없는 버전·손상 파일·과대 파일을 안전하게

- [ ] 마이페이지에 “내 데이터 안내”와 계정 탈퇴 요청 흐름을 추가한다. 탈퇴 시 삭제 대상, 법정 보존 대상,
  처리 예정일을 확인받는다.
- [ ] `editor-draft-recovery-plan`의 로그인·충전 왕복 복구 QA를 완료해 백업 기능과 임시 복구 기능의 목적을
  UI에서 명확히 구분한다.

### 완료 기준

- 계정이 보관하는 데이터와 브라우저에만 보관되는 데이터가 로그인 전후 동일하게 안내된다.
- 다른 브라우저에서 백업 파일을 가져와 핵심 편집 상태와 내보내기 결과를 재현할 수 있다.
- 사용자가 데이터 열람·삭제·탈퇴 요청을 시작할 수 있고 운영자가 처리 상태를 추적할 수 있다.
- 인증·충전 왕복 뒤 임시 편집본 복구가 실제 로그인과 결제 테스트에서 통과한다.

## Phase 3 — 결제 취소·환불·영수증 운영

### 설계

- [ ] 결제 상태를 `pending → paid → refund_requested → partially_refunded/refunded`로 확장하고 허용되는
  상태 전이와 순서가 뒤바뀐 webhook 처리 규칙을 문서화한다.
- [ ] 크레딧 원장에 구매 지급·사용·실패 반환·환불 회수를 구분하는 항목과 idempotency key를 둔다.
- [ ] 이미 사용한 크레딧의 환불 가능 범위, 잔액 부족 시 처리, 계정 제한, 부분 환불 정책을 확정한다.
- [ ] 전액·부분 환불, 청약철회 예외, 디지털 결과물 생성 후 처리, 크레딧 유효기간을 환불 정책과 약관에
  반영한다.

### 구현

- [ ] PayApp 취소/환불 알림을 별도 상태 전이로 처리하고 동일 알림 재전송에도 중복 회수가 발생하지 않게 한다.
- [ ] 관리자 화면에 결제 조회, 환불 요청·확정, 사유 입력, 크레딧 회수 결과, 작업자·시각 감사 로그를 제공한다.
- [ ] 마이페이지에 결제 금액, 상품, 결제일, 결제·환불 상태, 영수증 또는 거래 확인 경로를 제공한다.
- [ ] 결제 prepare, 결제 상태 조회, 코드 리딤에 사용자·IP 단위 rate limit과 이상 요청 로그를 적용한다.
- [ ] 정상 결제, 중복 feedback, 금액 변조, 순서 역전, 전액·부분 환불, 사용 후 환불을 자동 테스트한다.

### 완료 기준

- 한 결제의 지급·사용·환불·회수 내역을 원장과 감사 로그로 재구성할 수 있다.
- webhook이 중복되거나 순서가 바뀌어도 크레딧이 중복 지급·회수되지 않는다.
- 사용자와 운영자가 같은 결제·환불 상태를 확인할 수 있다.
- 실제 PayApp sandbox 또는 최소 금액 실결제로 결제→취소/환불 왕복을 검증한다.

## Phase 4 — CI·보안·모니터링·백업

### 자동 검증과 CI

- [ ] PR CI에 `check:text`, `tsc`, ESLint 오류 검사, Vitest, Android/iOS 슬롯·색상 검사를 연결한다.
- [ ] 로그인 → 편집 → 로그인/충전 왕복 → 복구 → export의 핵심 E2E를 staging에서 실행한다.
- [ ] 크레딧 예약·완료·실패 반환 동시성과 결제 webhook idempotency 테스트를 추가한다.
- [ ] RLS와 `SECURITY DEFINER` 함수의 anon/authenticated/service role 권한 회귀 테스트를 추가한다.
- [ ] Android APK·iOS `.ktheme` fixture의 필수 파일, manifest/plist, 리소스 경로를 회귀 검사한다.

### 운영 안전장치

- [ ] 중앙 오류 수집을 연결하고 인증 오류, 결제 실패율, export 실패율·지연, Cloud Run Job 실패를
  구분해 기록한다. 파일명·결제 원문·사용자 이미지 등 민감 정보는 전송하지 않는다.
- [ ] 결제·export 실패율과 연속 장애에 운영자 경보를 연결하고 테스트 알림을 확인한다.
- [ ] 운영 SMTP 발송 도메인·SPF·DKIM·DMARC와 가입·비밀번호 재설정 메일 전달률을 검증한다.
- [ ] 회원가입·로그인·민감 API에 CAPTCHA와 rate limit을 적용하고 우회·오탐 대응 경로를 둔다.
- [ ] Supabase Security/Performance Advisor를 확인하고 공개 schema, RLS, 함수 권한 경고를 해소한다.
- [ ] 운영자 MFA·최소 권한, service role/GCP/PayApp 비밀키 보관·교체·폐기 절차를 문서화한다.
- [ ] Supabase 백업/PITR와 GCS 보관 정책을 확인하고 목표 RPO/RTO에 맞춘 복구 리허설을 수행한다.
- [ ] staging export 부하 테스트로 동시 요청 상한, 평균·상위 지연, 실패율, 1회당 비용 상한을 측정한다.

### 완료 기준

- 보호 브랜치의 필수 CI를 통과하지 않으면 배포할 수 없다.
- 결제·인증·export 장애를 중앙 화면에서 확인하고 테스트 경보가 담당자에게 도달한다.
- 백업에서 핵심 계정·결제 데이터를 복원한 리허설 기록과 RPO/RTO가 존재한다.
- SMTP, CAPTCHA, Advisor, MFA, 비밀키, GCS lifecycle 설정을 운영 환경 체크리스트로 확인한다.

## 착수 순서

1. Phase 1 데이터 흐름표를 먼저 작성해 정책 문구와 보관·삭제 구현의 기준을 확정한다.
2. Phase 2 백업 파일 규격과 Phase 3 결제 상태·원장 설계를 병렬로 상세 설계할 수 있다.
3. Phase 3 결제 운영이 안정된 뒤 그 흐름을 대상으로 Phase 4 E2E·모니터링을 완성한다.
4. Phase 5 실기기 매트릭스와 운영 훈련을 통과하면 제한적 유료 출시를 승인한다.
5. 출시 후 `service-growth-plan`의 데이터로 Phase 6 작업의 순서와 실험을 결정한다.
