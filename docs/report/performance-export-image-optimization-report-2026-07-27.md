## 1. 요약

이번 작업은 편집 기능이나 화면 디자인을 바꾸지 않고, 이미지가 많거나 큰 프로젝트에서 반복되던 다운로드·디코딩·픽셀 복사·업로드·상태 조회를 줄이는 데 초점을 맞췄다.

주요 변화는 다음과 같다.

- 말풍선 원본과 나인패치 파싱 결과를 재사용해 편집 중 반복 로딩을 제거했다.
- 나인패치 분석 시 전체 이미지 대신 1px 테두리만 읽고, Base64 data URL 변환 없이 Blob을 직접 디코딩한다.
- 원격 에셋 서명 URL, Android/iOS 내보내기 슬롯, Android 빌드 입력 업로드를 제한된 동시성으로 병렬 처리한다.
- Android에서 동일한 Blob이 여러 출력 경로에 사용될 때 하나의 파일만 업로드한다.
- 추천 에셋 목록을 30초 동안 재사용하고, Android 가이드 이미지 전송량을 약 91% 줄였다.
- 장시간 APK 빌드의 상태 조회 간격을 늘려 인증 및 DB 조회 부하를 줄였다.
- 후속 리뷰에서 확인된 iOS manifest 호환 문제와 Android 확장 용량 제한 우회를 수정했다.

## 3. 말풍선 미리보기와 편집 성능

### 기존 동작

말풍선 이미지를 표시할 때마다 파일 또는 URL을 읽고, Blob을 Base64 data URL로 변환한 다음 이미지를 다시 디코딩했다. 이후 전체 이미지 픽셀을 `getImageData`로 복사해 나인패치 테두리를 분석했다.

채팅방 미리보기는 마커나 geometry 같은 편집값이 바뀔 때도 네 종류의 말풍선 원본을 다시 읽고 파싱했다. 같은 화면을 다시 열거나 여러 프리뷰가 같은 파일을 요청할 때도 작업이 중복됐다.

### 변경 동작

- 말풍선 원본 파일이 바뀔 때만 다시 읽고, 편집값 변경은 기존 캔버스로 다시 그린다.
- 말풍선 네 종류를 `Promise.all`로 동시에 준비한다.
- 한 슬롯 로딩이 실패해도 나머지 말풍선은 계속 표시한다.
- 최근 파싱 결과 최대 24개를 LRU 방식으로 보관한다.
- 같은 파일에 대한 동시 요청은 진행 중인 Promise까지 공유한다.
- 서명 URL 쿼리 문자열이 갱신되어도 동일 원본 경로라면 캐시를 재사용한다.

### 나인패치 처리

- Blob을 Base64 문자열로 변환하지 않고 `createImageBitmap`으로 직접 디코딩한다.
- 마커 및 유효성 검사는 전체 픽셀이 아니라 상·하·좌·우의 1px 테두리만 읽는다.
- 예를 들어 2000×2000 이미지의 경우 약 400만 픽셀 대신 약 8000픽셀만 JS 메모리로 복사한다.
- Base64 변환 과정에서 발생하던 약 33%의 임시 데이터 팽창도 제거한다.

### 사용자 영향

- 말풍선 마커 드래그가 더 부드러워진다.
- 말풍선 편집 화면을 다시 열 때 파싱 결과를 재사용하므로 표시가 빨라진다.
- 큰 말풍선 이미지를 사용할수록 CPU 및 메모리 절감 효과가 커진다.
- 화면과 최종 내보내기 결과의 의미는 기존과 동일하게 유지된다.

## 4. 템플릿 및 원격 에셋 로딩

### 서명 URL 요청 병렬화

기존에는 최대 50개씩 묶은 서명 URL 요청을 순차 실행했고, 배치 API가 없는 환경의 단건 fallback도 순차 실행했다.

현재는 다음 제한으로 병렬 실행한다.

- 서명 URL 배치 크기: 50개
- 배치 요청 동시성: 4
- 단건 fallback 동시성: 6
- 기존 클라이언트 서명 URL 캐시: 9분 유지

결과 순서는 공용 `mapWithConcurrency`가 입력 순서대로 보존한다.

### 추천 에셋 페이지 캐시

활성화된 공용 추천 에셋 목록을 동일한 플랫폼·에셋 종류·슬롯·페이지 조건별로 30초 동안 프로세스 메모리에서 재사용한다.

- TTL: 30초
- 최대 항목: 128개
- 응답 헤더: `Cache-Control: private, max-age=30`
- 서명 URL 유효기간 10분보다 짧게 유지해 만료 URL이 장기간 남지 않도록 한다.

### 사용자 영향과 트레이드오프

- 에셋이 많은 템플릿을 열 때 초기 준비 시간이 줄어든다.
- 여러 슬롯에서 같은 추천 목록을 열 때 응답이 빨라진다.
- 관리자가 추천 에셋을 활성화하거나 비활성화한 직후에는 기존 사용자가 최대 약 30초 동안 이전 목록을 볼 수 있다.
- 캐시는 인스턴스별 best-effort 캐시이므로 정확성이 캐시 적중에 의존하지 않는다.

## 5. Android 및 iOS 내보내기 준비 병렬화

기존에는 이미지 슬롯을 하나씩 순차 처리해 각 슬롯의 fetch·디코딩·리사이즈·나인패치 변환 지연이 누적됐다.

현재는 Android와 iOS 모두 이미지 슬롯을 최대 6개씩 동시에 처리한다.

- 출력 순서는 기존 슬롯 순서를 유지한다.
- 무제한 병렬화로 인한 브라우저 연결 및 메모리 사용 증가를 막기 위해 동시성을 제한한다.
- Android 나인패치 내보내기도 data URL을 거치지 않고 Blob을 직접 디코딩한다.

이미지와 원격 에셋이 많은 프로젝트일수록 내보내기 버튼을 누른 뒤 업로드 또는 빌드 요청이 시작되기 전까지의 대기가 줄어든다.

## 6. Android 중복 업로드 및 빌더 입력 최적화

Android는 하나의 이미지가 여러 density 또는 화면 크기 경로로 출력될 수 있다. 기존에는 동일 Blob이어도 출력 경로마다 별도의 multipart 파일을 만들었다.

현재는 동일 Blob 객체에 하나의 `file-N` 필드를 할당하고, manifest의 여러 출력 경로가 그 필드를 공유한다.

- 브라우저는 동일 바이트를 한 번만 업로드한다.
- 동기 Android 내보내기 서버는 필드별 바이트를 한 번만 읽는다.
- 비동기 Android 빌더도 GCS 오브젝트와 서버 에셋을 소스별로 한 번만 읽는다.
- 출력 manifest의 각 경로는 그대로 유지되므로 APK 내부 리소스 구성은 바뀌지 않는다.

예를 들어 같은 5MB Blob이 네 경로에 쓰이면 기존에는 약 20MB를 업로드했지만, 현재는 약 5MB만 업로드한다.

## 7. Android 빌드 입력 병렬 업로드

기존에는 `bundle.json`을 올린 다음 입력 파일을 하나씩 GCS에 업로드했다. 파일 수만큼 네트워크 왕복 지연이 누적된 뒤에야 빌더 작업을 시작했다.

현재는 다음과 같이 처리한다.

- `bundle.json`과 입력 파일 업로드를 함께 시작한다.
- 입력 파일은 최대 8개씩 병렬 업로드한다.
- 모든 업로드가 성공한 뒤 빌더 작업을 시작한다.

Android 내보내기 한 건에 수십 개의 입력 오브젝트가 있는 경우, 내보내기 요청에서 APK 빌드 큐 등록까지의 시간이 줄어든다.

## 8. 내보내기 API와 상태 폴링

### 미들웨어 제외

`/api/export` 경로를 공용 Supabase 세션 미들웨어 matcher에서 제외했다. 최대 50MB의 multipart 본문과 반복 상태 조회가 불필요하게 공용 미들웨어를 통과하지 않는다.

내보내기 Route Handler가 직접 인증을 검사하므로 인증을 생략하는 변경은 아니다.

### 상태 폴링

기존에는 최대 12분 동안 3초마다 상태를 조회해 최대 약 240회의 요청이 발생했다.

현재 간격은 다음과 같다.

- 시작 후 30초까지: 3초
- 30초부터 2분까지: 5초
- 2분 이후: 10초
- 전체 제한: 기존과 동일한 12분

12분 전체를 사용하는 작업은 상태 조회가 대략 240회에서 약 88회로 줄어든다. 인증과 `export_jobs` DB 조회 부하가 약 60% 이상 감소한다.

트레이드오프는 빌드 시작 후 2분이 지난 상태에서 완료 또는 단계 변경이 화면에 최대 약 10초 늦게 표시될 수 있다는 점이다. APK 생성 시간 자체는 바뀌지 않는다.

## 9. Android 가이드 이미지 최적화

실제 사용하는 Android 가이드 PNG 네 장을 표시 크기에 맞춘 1280px WebP로 변경했다.

| 이미지 | 기존 PNG | 현재 WebP | 감소율 |
| --- | ---: | ---: | ---: |
| 템플릿 갤러리 | 384,437B | 31,428B | 91.8% |
| 배경 편집 | 302,827B | 36,232B | 88.0% |
| 말풍선 편집 | 409,898B | 45,518B | 88.9% |
| APK 내보내기 | 353,626B | 19,564B | 94.5% |

총합은 약 1.45MB에서 133KB로 줄어 약 90.9% 감소했다.

원본 PNG 8개는 배포 경로인 `public`에서 `assets/guide-sources`로 이동했고, 실제 사용하는 네 장만 WebP로 배포한다. 에셋 변경 시 `npm run assets:guide`로 다시 생성할 수 있다.

## 10. 후속 리뷰 수정

### iOS manifest 고유 필드

Android 공유 필드 최적화를 iOS에도 그대로 적용하면 iOS API가 중복 필드를 `invalid_manifest`로 거부했다.

현재는 다음과 같이 플랫폼 계약을 분리한다.

- Android: 동일 Blob에 동일 필드 사용
- iOS: 출력 경로마다 고유한 `file-N` 필드 사용

동일 이미지를 `@2x`, `@3x` 또는 여러 아이콘 경로에 사용하는 정상적인 iOS 프로젝트가 manifest 오류로 실패하지 않는다. iOS는 기존 서버 계약을 유지하므로 Android와 같은 중복 업로드 절감은 적용하지 않는다.

### Android 확장 용량 제한

기존 공유 필드 검사에서는 실제 업로드 바이트만 한 번 계산했다. 공격자가 하나의 20MB 필드를 최대 300개 경로에서 참조하면 50MB 요청 제한을 통과하면서 빌더가 약 6GB를 출력할 수 있었다.

현재는 동기·비동기 Android 요청 모두 다음 원칙을 적용한다.

- 필드 바이트는 한 번만 업로드하고 한 번만 읽는다.
- 용량 제한은 manifest의 각 출력 경로에 실제로 확장되는 바이트를 누적한다.
- 확장된 총크기가 50MB를 넘으면 `export_payload_too_large`와 HTTP 413으로 거부한다.

정상 사용자도 큰 이미지 하나를 여러 출력 경로에서 반복 사용해 확장 크기가 50MB를 넘으면 기존보다 일찍 오류를 볼 수 있다. 이 경우 원본 이미지 크기를 줄여야 한다.

## 12. 결론

이번 브랜치는 편집 모델이나 최종 테마 형식을 바꾸지 않고, 중복 I/O와 직렬 처리 병목을 제거했다. 가장 직접적인 사용자 체감은 말풍선 편집의 부드러움, 에셋이 많은 템플릿의 로딩 속도, Android/iOS 내보내기 준비 시간, Android APK 업로드 및 큐 등록 시간에서 나타날 것으로 예상된다.

후속 리뷰 수정으로 iOS manifest 호환성을 보존하고 Android 빌더의 확장 용량 우회를 차단해, 성능 개선이 기존 내보내기 계약과 자원 제한을 훼손하지 않도록 보완했다.
